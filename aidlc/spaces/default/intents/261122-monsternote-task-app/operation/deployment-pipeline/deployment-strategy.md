# Deployment Strategy — Deployment Pipeline

## 1. 採用する戦略: その場での置き換え（in-place）

この唯一の環境`dev`は低トラフィック（開発者本人＋少人数の試験運用のハンター・依頼元）であり、複数バージョンを同時に稼働させてトラフィックを振り分ける理由が無い。そのため、**blue/greenでもcanaryでもなく、`cdk deploy`による「その場での置き換え」1種類だけを採用する**。

| 戦略 | 採用するか | 理由 |
|---|---|---|
| In-place（`cdk deploy`でスタックを更新） | ✅ 採用 | 単一環境・低トラフィック・無料枠の制約の中では、追加の環境やルーティング層を持つこと自体が費用・複雑さの増加にしかならない |
| Blue/Green | ❌ 不採用 | 2系統の環境を同時に維持するコストが発生し（Lambdaのエイリアス＋CodeDeploy、または環境の二重化）、無料枠の前提（project.md）と相容れない。トラフィックを切り替える相手（複数ユーザーの段階的な移行）も存在しない |
| Canary | ❌ 不採用 | 同上。少人数の試験運用では、一部の利用者にだけ新しいバージョンを見せる意味が薄く、むしろ「ハンターと依頼元で違う版が動いている」という混乱の原因になりうる |

## 2. デプロイの単位

CDKスタック単位（Auth・Web・Data・Api・WebContent、計5スタック）。`cdk deploy`は変更があったスタックだけを更新し、CloudFormationのchange setで差分適用する。これは「その場での置き換え」の具体的な実装であり、CDKの標準的な挙動そのものである。

## 3. デプロイの手順（概要。詳細は`rollback-runbook.md`・team.md Deployment節）

1. `cdk diff`で変更内容を確認し、無料枠からはみ出す恒常課金リソースが無いか、project.mdのMandatedどおり確認する。
2. 人に変更内容とコストの見込みを示し、デプロイの実行可否を確認する（毎回。project.md Mandated）。
3. 承認を得てから、開発者のパソコンから`cdk deploy`（AWS CLI `default`プロファイル、`ap-northeast-1`）。
4. デプロイ完了後、git タグ（例: `v0.1.0`）を付ける。
5. `npm run smoke`（`scripts/smoke.ts`）を実行する。

## 4. 中断（abort）条件

- **`npm run smoke`が失敗した場合、このデプロイを「前進」とは扱わない。** 次のデプロイで直接修正を試みるのではなく、`rollback-runbook.md`の手順に従って前のタグへ戻すかどうかを人に確認する。
- `cdk deploy`自体がCloudFormationのエラーで失敗した場合（スタックが`ROLLBACK_COMPLETE`等になる）、CDK/CloudFormationが自動的にそのスタックを変更前の状態に戻す（CloudFormationの標準動作）。空になった失敗スタックを消してやり直すかどうかも人に確認する（実例: `docs/05-construction.md` §8「デプロイの1回目: 失敗」）。
- DynamoDBのテーブルを作り直す（キー設計の変更等でテーブルの置き換えが必要になる）ような、データを消す可能性のある変更は、`cdk deploy`を実行する前の時点で、その変更内容自体を人に個別に確認する（通常のデプロイ確認とは別に、明示的に伝える）。

## 5. スモークテストの内容（`npm run smoke`。`scripts/smoke.ts`の実装どおり）

| # | 確認内容 |
|---|---|
| 1 | ハンター・依頼元の2つの画面が開け、`config.json`の`apiBaseUrl`がAPIのURLと一致する |
| 2 | 試験用ハンターアカウントでログインできる（Cognito） |
| 3 | 写真を受け付け、署名付きPOSTでS3へアップロードし（CORSヘッダーの確認を含む）、完了を知らせる |
| 4 | 報告を送信できる |
| 5 | ハンターの一覧に10秒以内に「確認中」が出る（EventBridgeの配達） |
| 6 | 依頼元でログインし、一覧に出た報告を承認できる |
| 7 | ハンターの一覧が10秒以内に「承認」になる |

負荷はかけない（数十リクエスト程度、project.mdのForbidden「NEVER run load tests that could exceed the Free Tier」どおり）。この7手順がすべて通ることを、デプロイ完了の唯一の基準とする。

## 6. 将来のトラフィック制御（今回は不要）

利用者が増え、複数バージョンの共存やカナリアリリースが必要になった場合は、Lambdaのエイリアス＋重み付きルーティング、またはAPI Gatewayのステージ分割が候補になる。現時点では該当する運用上の必要性が無く、設計もしない。
