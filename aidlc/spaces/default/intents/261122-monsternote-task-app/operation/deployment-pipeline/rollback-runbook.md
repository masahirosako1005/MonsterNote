# Rollback Runbook — Deployment Pipeline

## 1. 前提

このプロジェクトは単一環境（`dev`）・手動デプロイ（team.md・project.md）。自動ロールバック機構（CodeDeployのトラフィックシフト失敗検知等）は無く、戻すかどうかの判断・実行も人が行う。

## 2. デプロイのたびに行うこと（戻すための準備）

- `cdk deploy`が成功し、`npm run smoke`が通ったら、その時点のコミットに **gitタグ**（例: `v0.1.0`、`v0.2.0`…セマンティックバージョニングにこだわらず、連番で増やす）を付ける。
- タグを付けた時点のコミットハッシュと、そのとき`cdk diff`で示されたスタックごとの変更内容を、`docs/05-construction.md`のOperationフェーズの節に記録する（教材としての記録。team.mdの標準的なドキュメント化の慣行）。

## 3. 戻す手順（通常のロールバック）

1. **人に確認する**: どのタグへ戻すか、戻す理由（何が壊れたか）を明示したうえで、「このタグのコードで`cdk deploy`し直してよいか」を確認する。project.mdのMandated「デプロイ前に必ず人に確認する」はロールバックにも同様に適用する。
2. 確認が取れたら、ロールバック先のタグをチェックアウトする（作業ブランチを切ってチェックアウトし、mainを直接動かさない）。
3. `npm run verify`をそのタグのコードで実行し、ローカルでの確認が通ることを確かめる。
4. `cdk diff`で、現在のAWS上の状態とロールバック先のコードとの差分を確認する（特にDynamoDBのテーブル定義やIAMの変更点に注意する）。
5. 差分の内容を人に示し、再度デプロイの実行可否を確認する。
6. `cdk deploy`を実行する。
7. `npm run smoke`で動作を確認する。
8. 戻した事実と理由を`docs/05-construction.md`に記録する。

## 4. データを消す変更が関わる場合の追加確認（DynamoDB）

DynamoDBのテーブルは全て`RemovalPolicy.RETAIN`（`infra/lib/data-stack.ts`）で作られており、スタックを削除してもテーブル自体は残る。ただし、**テーブルの置き換え**（パーティションキーの変更など、CloudFormationが「置き換え」と判定する変更）を伴うデプロイやロールバックは、新しいテーブルが作られ、古いテーブルのデータは自動的には引き継がれない。

- このような変更を含むデプロイ・ロールバックを行う前には、**その変更がテーブルの置き換えを伴うかどうかを`cdk diff`で確認し、伴う場合はその旨を明示して人に確認する**（project.mdのMandated・team.mdの戻し方の節に明記された固有の確認事項）。
- 今回（2026-11-26時点）は、U1のスケルトン確認のとき以降、U2〜U4の内容はまだ一度も`dev`へデプロイされていない（`environment-provisioning/validation-report.md`参照）。したがって、この「テーブル置き換えを伴うロールバック」はまだ実例が無い。U2以降の初回デプロイの際には、7個（U1）→12個（U2。U3はテーブルを増やさない）→14個（U4）とテーブルが追加される差分になる想定で、いずれも**追加**であり既存テーブルの置き換えではないと設計時点では見込んでいるが、実際の`cdk diff`の結果で必ず確認する。

## 5. 失敗したスタックの後始末

`cdk deploy`の途中でエラーになり、CloudFormationが自動的にロールバックした結果、スタックが`ROLLBACK_COMPLETE`（中身が空）になることがある（実例: `docs/05-construction.md` §8、Cognitoの`ALLOW_REFRESH_TOKEN_AUTH`の競合）。この状態のスタックは再度の`cdk deploy`を受け付けないため、次の手順を踏む:

1. 空の`ROLLBACK_COMPLETE`スタックであることを確認する（中身のリソースが無いことを`cdk diff`やコンソールで確かめる）。
2. 人に「このスタックを削除してやり直してよいか」を確認する（project.mdのMandated。削除が対象であるため特に明示する）。
3. 確認後、スタックを削除し、原因を修正したコードで`cdk deploy`をやり直す。

## 6. 戻せないもの・留意事項

- S3バケット（写真・画面）・DynamoDBテーブルは`RETAIN`のため、スタックの削除では消えない。意図して中身ごと消す場合は、個別に人の確認を取ったうえでバケットの中身・テーブルの項目を消してからスタックを削除する。
- Cognitoのユーザープールも`RemovalPolicy.RETAIN`。アカウント自体を戻す操作は、インフラのロールバックとは別に、`/v1/admin/accounts`系のAPIまたはCognitoコンソールから個別に行う。
- 本番相当の環境が無いため、ロールバックの影響範囲は常に「唯一の`dev`環境の、少人数の試験運用利用者」である。影響が限定的であることは、手動の確認フローで十分対応できる規模だと判断している根拠の1つ（team.md Deployment節）。
