入力: `docs/05-construction.md`・`docs/06-operation.md`（実機で発生した出来事の記録）、`operation/observability-setup/alarms.md`、`operation/incident-response/*.md`、`operation/performance-validation/*.md`。本ステージはこれらを再調査するのではなく、プロジェクト全体を振り返って「設計・前提と、実際に動いているものがどこでずれたか」を1つにまとめる。

## 1. 今回のプロジェクトで実際に見つかった設計とのずれ（時系列）

| # | 発生段階 | ずれの内容 | 発見方法 |
|---|---|---|---|
| 1 | Build and Test | U2のハンター報告画面が、承認済みのInteraction Spec（7〜8画面）と異なる3画面構成で作られており、しかもバックエンドが必須とする項目（尻尾の写真・年齢区分・捕獲方法・捕獲日時等）を一度も収集していなかった。実際のバックエンドへの送信は常に422で失敗する状態だった | 単体・E2Eどちらも必須項目を検証していなかったため、手作業でバックエンドの検証ロジックとフロントの送信内容を突き合わせて発見 |
| 2 | Deployment Execution | `infra/lib/api-stack.ts`のアラーム設計（全関数のエラーを1つのアラームに入れ子の数式でまとめる）が、CloudFormation上で平らに展開されてCloudWatchの指標数上限（10個）を超え、`cdk deploy`が失敗した | 実際に`cdk deploy`してCloudFormationの検証を通すまで分からなかった（`cdk diff`では検出できない） |
| 3 | Deployment Execution | `scripts/smoke.ts`（実機確認用スクリプト）が、#1の修正で追加された必須項目を送っておらず、デプロイ後のスモークテストが422で失敗した | スモークテスト実行時に発覚 |
| 4 | Incident Response | 3つのCloudWatchアラームのSNS通知先に、実際には誰も購読していなかった（`ALARM_EMAIL`が空欄のまま、どの`cdk deploy`にも`-c alarmEmail=...`が渡されていなかった） | `infra/.env.local`と実際のデプロイ記録を突き合わせ、AWS上の購読状況を直接確認して発覚 |
| 5 | Performance Validation | `scripts/perf-check.ts`（本ステージの直前に新規作成した計測スクリプト）が、固定の緯度経度・種類で報告を送信する設計になっており、同日の`npm run smoke`実行分と重複の疑いで衝突し、1回目の実行が失敗した | 実行時のエラーで即座に発覚 |

## 2. 共通するパターン（個別のバグの集まりではない）

上の5件はそれぞれ別の層（画面、インフラ設定、実機確認スクリプト×2、通知の配線）で起きているが、**同じ構造のずれ**が繰り返されている:

> **「ある時点の前提を埋め込んだ成果物（画面の実装、アラームの設計、確認用スクリプト）が、その後ほかの場所で前提が変わっても、追従して更新する仕組みが無いまま取り残される」**

- #1: バックエンドの必須項目が増えた（U2設計時点） → 画面側がその前提のまま放置された。
- #3: 画面側の送信内容が直った（#1の修正） → 実機確認スクリプト（`smoke.ts`）がその前提のまま放置された。
- #5: 実機確認スクリプト（`smoke.ts`）の座標の使い方が、別の新しい実機確認スクリプト（`perf-check.ts`）に流用された → 重複判定という別の制約と衝突することが考慮されずに放置された。
- #2: 関数の数が増える（Unit追加のたびの既知の傾向）という前提の変化に対し、アラーム設計側の「入れ子で回避できる」という誤った対策が、実際にCloudFormationでどう展開されるかを検証しないまま埋め込まれた。
- #4: 「アラームを作る」という決定と「実際に誰かが購読する」という決定が別々の工程（CDKコード vs デプロイコマンドのコンテキスト引数）に分かれており、両方が揃って初めて意味を持つという依存関係が、どちらの成果物にも明示されていなかった。

**この共通パターンは、`project.md`/`team.md`の`## Corrections`にすでに記録されている個別の学び（「新しいUnitのNFR Designを書く前に実際のinfrastructure-specification.mdを確認する」等）と同じ根っこを持つ**。個々の学びは「次に書くときに確認する」という対策だが、今回の5件はいずれも「すでに存在する成果物が、前提の変化に追従していない」という、書いた後の整合性維持の問題であり、書く前の確認だけでは防げない種類のずれである。
