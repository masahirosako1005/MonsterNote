# RAID Log — MonsterNote

入力: `ideation/intent-capture/intent-statement.md`（intent-statement）、`ideation/market-research/`（competitive-analysis・market-trends・build-vs-buy）、feasibility-assessment.md、constraint-register.md、feasibility-questions.md（Q1〜Q9）。

## Risks（リスク）

| ID | リスク | 起きやすさ | 影響 | 対策 |
|---|---|---|---|---|
| R1 | 1 か月で最初の版が間に合わない（範囲が大きい） | 高 | 高 | Scope Definition で機能を絞る（Q8） |
| R2 | 写真から雌雄を自動判別するロジックを、期限内・費用内で作れない | 高 | 中 | 最初の版はハンターが選ぶ方式（「不明」も可）にし、解析ロジックは次の版で検討する（Intent Capture の Q28 の代替策） |
| R3 | 捕獲後の写真で、種類（クマ・イノシシ・シカ）が正しく判別されない | 中 | 中 | 早い段階で実際の写真で試す。判別できないときはハンターが直す（Intent Capture の Q12） |
| R4 | 別の角度から撮った同じ個体を見逃し、重複の疑いが見つからない | 中 | 高 | 場所・日時の近さ、マーキング・尻尾の提出と組み合わせ、最終判断は依頼元が行う |
| R5 | 画像解析の処理が、関数のメモリの上限（128〜256 MB）に収まらない | 中 | 中 | 解析ロジックを作る場合は、ルールの見直しを人に確認する |
| R6 | アカウント作成から 12 か月を過ぎ、無料枠の対象外のサービスで費用が増える | 中 | 低 | タグ別の費用を毎月確認する（Q3）。見込みは月 100 円以内 |
| R7 | ハンターの個人情報・位置情報をお客様に見せることで、同意の不備や情報の漏れが起きる | 低 | 高 | 利用開始時の同意（Q9）、見せる相手を限る認証 |
| R8 | 共用アカウントで、mononoke のリソースに誤って影響する | 低 | 高 | MonsterNote のリソースにはすべてタグを付け、mononoke のリソースには触れない |
| R9 | 公開の API に大量のアクセスが来て、費用が増える | 低 | 中 | API のスロットリングを設定する |

## Assumptions（仮定）

| ID | 仮定 | 確かめ方 |
|---|---|---|
| A1 | 試験運用の報告は月 50 件未満、写真は月 150 枚程度 | 試験運用中に件数を数える |
| A2 | AWS の画像認識サービスで、クマ・イノシシ・シカを判別できる | 実際の写真で試す |
| A3 | 東京リージョンの画像認識の料金は、米国東部と同程度 | AWS の料金ページで確認する |
| A4 | 高齢のハンターがスマホのブラウザで位置情報とカメラの利用を許可できる | 試験運用で確かめる |
