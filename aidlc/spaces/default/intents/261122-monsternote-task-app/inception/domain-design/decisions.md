# Decisions（設計の決定記録 ADR）— Domain Design

入力: components.md、domain-design-questions.md（Q1〜Q6）、`inception/requirements-analysis/requirements.md`（requirements）、`inception/user-stories/stories.md`（stories）、`inception/practices-discovery/team-practices.md`（team-practices）。

日付はすべて 2026-11-23、状態はすべて Accepted（まとめの確認で「Looks correct」）。

## ADR-001: 報告の内容（Reporting）と状態（Review）を別の部品にする

- **Context** — 報告の状態は、2 組織の依頼元が操作する（requirements FR8.1）。先に受け付けた操作だけを有効にし（FR8.6）、10 秒の取り消しがある（FR8.5）。報告の内容は送ったあと変えない（stories US5.2）。内容と状態を 1 つの部品に置くと、確認の決まりと報告の受け付けの決まりが混ざる。
- **Decision** — Review が ReviewDecision（状態・理由・確認した人・取り消しの期限）を持ち、状態を決める。Reporting は内容（Report・Photo）だけを持つ。Reporting は保存したら「報告が保存された」知らせを Review に送り、Review が確認中の記録を作る（Q1 の A）。
- **Consequences** — 良い点: 同時操作・取り消しの決まりが Review に集まり、TDD でまとめて試せる。報告の内容は書き込み 1 回だけになる。悪い点: 内容と状態が別の部品にあるため、一覧は 3 つの部品のデータを合わせる必要がある（ReportCatalog で組み立てる。ADR-010）。保存の知らせが届くまでのわずかな間、状態が存在しない。**保存の知らせが失われると、Review に確認中の記録ができず、その報告は依頼元が承認も却下もできない**（ADR-008 で NFR Design に引き継ぐ）。
- **Alternatives Rejected** — Reporting が状態も持ち、Review は状態の変更を頼むだけ（Q1 の B）: 確認の決まりが Reporting に入り、部品の境目があいまいになるため選ばなかった。

## ADR-002: 種類の判別と重複の判定を、報告の部品から分ける

- **Context** — 種類の判別は AWS の画像認識サービスに頼り、しきい値は試験で調整する（requirements FR3.1・FR3.5、A-7）。重複の判定は一番の課題で、Should で写真・月の輪の照合が加わる（FR11・FR12）。どちらも報告の受け付けとは変わる理由が違う。
- **Decision** — SpeciesDetection と DuplicateDetection を独立した部品にする（Q2 の A）。
- **Consequences** — 良い点: 判別のサービスの差し替えや、重複の判定方法の追加が、Reporting に影響しない。それぞれを単独で試せる。悪い点: 部品の数が増え、Reporting から 2 つの部品をその場で呼ぶ（送信の時間に影響する。requirements NFR2 の 10 秒以内で確かめる）。
- **Alternatives Rejected** — 判別だけ分ける（Q2 の B）、両方とも Reporting に入れる（Q2 の C）: Should の追加で Reporting が大きく変わり、一番の課題の部分を独立して試しにくいため選ばなかった。

## ADR-003: 重複の判定は「送信の前はその場、保存の後は知らせで再判定」にし、判定用の索引を自分で持つ

- **Context** — 送信の前にハンターへ知らせる必要がある（FR7.1）ため、その場で答えが要る。一方、ほぼ同時に送られた 2 件は送信の前の判定では見つからない（FR6.4）。DuplicateDetection が判定のたびに Reporting を呼ぶと、Reporting → DuplicateDetection → Reporting の呼び出しの輪ができる。
- **Decision** — 送信の前は Reporting が DuplicateDetection をその場で呼ぶ。保存の後は「報告が保存された」知らせで DuplicateDetection が非同期に再判定し、双方に印を付ける（Q4 の A）。DuplicateDetection は比べるための索引（ReportFootprint: 種類・場所・日時）を知らせから作って自分で持ち、Reporting を呼ばない。Review は却下を確定したときに「報告が却下された」知らせを、10 秒以内に却下を取り消したときに「却下が取り消された」知らせを送り、DuplicateDetection は索引から外す・戻す（レビューの R-02 で追加）。
- **Consequences** — 良い点: 呼び出しの輪がない。送信の前の答えが速い（自分の索引だけを見る）。取り消された報告も、再び比べる相手に戻る。悪い点: 索引は報告の写しで、知らせが遅れると直前の報告を見落とす（保存の後の再判定で補う）。**保存の知らせが失われるとその報告は比べる相手にならず、取り消しの知らせが失われると取り消された報告が比べる相手から漏れる**（ADR-008 で NFR Design に引き継ぐ）。
- **Alternatives Rejected（取り消しの扱い）** — 却下の知らせを 10 秒の猶予が終わってから送る案: 猶予の間に送られた同じ個体の報告と比べてしまい、却下予定の報告が疑いの相手になるため選ばなかった。
- **Alternatives Rejected** — 送信のときだけ判定し、保存の後は 1 日 1 回まとめて再判定（Q4 の B）: 依頼元が疑いに気づくのが最大 1 日遅れるため選ばなかった。DuplicateDetection が Reporting を直接読む案: 呼び出しの輪ができるため選ばなかった。

## ADR-004: 操作の記録は、知らせ（イベント）で AuditLog に集める

- **Context** — requirements NFR14 は、報告の送信、承認・却下、取り消し、アカウントの操作、設定の変更、データの削除を記録するよう求める。記録の形を各部品が知ると、記録の項目を変えるたびに全部品が変わる。
- **Decision** — 各部品は「〜が起きた」知らせを送り、AuditLog が受け取って変更できない記録として保存する（Q3 の A）。パスワードと写真そのものは記録しない。
- **Consequences** — 良い点: 記録の形が 1 か所に集まる。各部品は記録の失敗で本来の操作を止めない。悪い点: 知らせが失われると記録が欠ける。知らせを確実に届ける仕組み（再送など）を NFR Design で決める必要がある。
- **Alternatives Rejected** — 各部品が AuditLog を直接呼ぶ（Q3 の B）: 記録の失敗が本来の操作を止めうるため選ばなかった。各部品が自分の記録を持つ（Q3 の C）: 管理者が 1 か所で見られないため選ばなかった。

## ADR-005: 画面は 3 つのアプリに分け、共通の部品集 UiKit を共有する

- **Context** — ハンター（スマホ、文字 20px・ボタン 64px）、依頼元（パソコンとスマホ、文字 16px）、管理者（パソコン）は、使う機器・画面の大きさ・操作がそれぞれ違う（refined-mockups、requirements NFR7・NFR9）。
- **Decision** — HunterApp・RequesterApp・AdminApp の 3 つの Web アプリに分ける（Q5 の B）。ボタン・ダイアログ・テーマ・アクセシビリティの決まりは、3 つが共有する UiKit にまとめる。UiKit の部品集（MUI）は Refined Mockups の Q1 で決定済みの前提。コードの置き場所と配置は Units Generation で決める（レビューの R-08 で移した）。
- **Consequences** — 良い点: 利用者ごとに画面を小さく保てる。ハンターのアプリに管理者の機能のコードが入らない。悪い点: 公開するアプリが 3 つになり、ビルドと配置の設定が増える（Units Generation・Infrastructure Design で、費用が無料枠に収まるかを確かめる）。共通部分は UiKit を通さないと重複する。
- **Alternatives Rejected** — 1 つのアプリに 3 つの区画（Q5 の A）: 人が 3 つに分けることを選んだ。ログイン後の振り分けが 1 か所で済む利点はあるが、採らなかった。

## ADR-006: 試験運用の終わりの削除は、データを持つ各部品が自分のデータを消す

- **Context** — requirements FR10.2 は、試験運用が終わったら報告と写真を削除することを求める。データは Reporting・SpeciesDetection・DuplicateDetection・Review・ReportCatalog に分かれて持たれる。
- **Decision** — データを持つ各部品が自分のデータを消す機能を持ち、AdminApp が順に呼ぶ（Q6 の A）。対象は Reporting（報告・写真）、SpeciesDetection（判別の結果）、DuplicateDetection（索引・疑い）、Review（確認の記録）、ReportCatalog（一覧）の 5 つ（レビューの R-05 で SpeciesDetection を明記）。AuditLog の記録は、削除の操作そのものを記録として残す（削除後も残すかは Functional Design で決める）。
- **Consequences** — 良い点: データの持ち主だけがそのデータを消すので、持ち主の決まりが守られる。悪い点: 途中で失敗すると一部だけ消えた状態になる。順番とやり直し方を Functional Design で決める必要がある。
- **Alternatives Rejected** — 削除専用の部品がすべてのデータを直接消す（Q6 の B）: 持ち主以外がデータを触ることになり、部品の境目が崩れるため選ばなかった。

## ADR-007: 役割の確認は、ログインの証明に入れた役割を各部品が読んで行う（レビューの R-03）

- **Context** — requirements NFR4 は、承認・却下は依頼元だけ、設定と記録の閲覧は管理者だけ、ハンターは自分の報告だけ、と定め、画面で隠すだけでなく API でも確かめることを求める。API を持つ部品は Accounts のほかに 7 つあり、役割を誰がどう確かめるかが決まっていなかった。
- **Decision** — Accounts がログインのときに、利用者の ID・役割・所属を入れた「ログインの証明」（有効期限 1 時間）を発行する。API を持つ各部品は、呼ばれるたびに証明が正しいか（改ざんされていないか、期限内か）を確かめ、中の役割と ID で操作を許すかを決める。役割の確認のために Accounts を呼ばない。無効にしたアカウントには証明を出し直さないため、1 時間以内に使えなくなる（FR10.4）。
- **Consequences** — 良い点: 各部品が自分で確かめるため、1 つの部品の確認漏れが全体に広がらない。Accounts が一時的に止まっても、発行済みの証明の期限内は他の部品が動く。悪い点: 無効化の反映が最大 1 時間遅れる（requirements A-8 で受け入れ済み）。各部品に同じ確認の処理が要る（Functional Design・Code Generation で共通の処理にする）。**セキュリティ**: 証明の署名の確認を省くと、役割を偽った呼び出しを許す。証明の確認は各部品の API の入口で必ず行い、テスト（ハンターが承認の API を呼ぶと拒否される、など）で確かめる。
- **Alternatives Rejected** — 各部品が呼ばれるたびに Accounts に役割を問い合わせる案: 呼び出しが倍になり、Accounts が止まると全部が止まるため選ばなかった。認証の共通の入口を 1 つの部品として作る案: 配置の形（Units Generation の範囲）に依存するため、ここでは「各部品の入口で確かめる」という決まりだけを決めた。

## ADR-008: 知らせ（イベント）が失われたときの影響を明記し、届け方は NFR Design で決める（レビューの R-07）

- **Context** — この設計では、報告の保存・却下とその取り消し・状態の変化・重複の疑い・操作の記録を、知らせで部品の間に伝える（ADR-001・ADR-003・ADR-004・ADR-010）。知らせが失われると、部品ごとのデータが食い違う。
- **Decision** — 知らせが失われたときの影響を次のとおり明記し、確実に届ける方法（保存と知らせを同時に成り立たせる方法、再送、重複して届いたときの扱い）は NFR Design で必ず決める。
  | 失われた知らせ | 影響 |
  |---|---|
  | 報告が保存された → Review | 確認中の記録ができず、承認も却下もできない |
  | 報告が保存された → DuplicateDetection | その報告が比べる相手にならない（重複の見落とし） |
  | 報告が保存された → ReportCatalog | 一覧に出ない |
  | 却下・却下の取り消し → DuplicateDetection | 比べる相手から外れない・戻らない |
  | 状態が変わった → ReportCatalog | 一覧の状態が古いまま |
  | 各種 → AuditLog | 操作の記録が欠ける |
- **Consequences** — 良い点: 次のステージが何を守ればよいかがはっきりする。悪い点: この段階では「失われない」ことを保証していない。NFR Design で決めるまで、試験はこの影響を前提に組む。
- **Alternatives Rejected** — 知らせを使わず、すべてその場の呼び出しにする案: 呼び出しの輪（ADR-003）と、記録の失敗で本来の操作が止まる問題（ADR-004）が戻るため選ばなかった。

## ADR-009: 写真は報告の前に受け付け、24 時間たっても結び付かない写真は消す（レビューの R-01）

- **Context** — 種類の判別の結果は、送信の前の「種類の確認」の画面で見せる必要がある（FR3.1）。そのため、写真は報告より先にサーバーに届き、判別される。一方、下書きは残さない（FR2.9）。報告に結び付かない写真と判別の結果が残り続けるおそれがある。
- **Decision** — 写真の受け付けと判別の依頼は Reporting が受け持つ。写真を選ぶたびに HunterApp が Reporting に送り、Reporting は「まだ報告に結び付いていない写真」（reportId が空、送ったハンターの ID を持つ）として保存し、全身の写真なら SpeciesDetection に判別を頼む。報告の送信のときに写真へ reportId を入れる。24 時間たっても結び付かない写真は、Reporting が写真を消し、SpeciesDetection に判別の結果を消してもらう。
- **Consequences** — 良い点: 判別の結果を送信の前に見せられる。送られなかった写真がサーバーに残り続けない（費用と個人情報の両方）。悪い点: 作成をやめた写真も最大 24 時間はサーバーに残る。写真の持ち主（送ったハンター）の確認が要る（他人の写真の ID を報告に使えないようにする）。24 時間で消す仕組みは Functional Design・NFR Design で決める。
- **Alternatives Rejected** — 報告の送信のときに写真をまとめて送り、判別する案: 種類の確認の画面（送信の前）で判別の結果を見せられないため選ばなかった。画面の中（端末）で判別する案: AWS の画像認識サービスを使う決定（Intent Capture）と合わないため選ばなかった。

## ADR-010: 一覧は、読み出し専用の部品 ReportCatalog が知らせから組み立てる（レビューの R-04）

- **Context** — 依頼元の一覧は、内容（Report）・状態（ReviewDecision）・重複の疑い（DuplicateSuspicion）・手入力の印で絞り込み、新しい順に 1 ページ 50 件に分ける（FR8.1・FR8.2）。ハンターの一覧も内容と状態を合わせる（FR9.1）。画面が 3 つの部品から集めて組み立てると、絞り込みとページ分けを同時に効かせられない。
- **Decision** — 読み出し専用の部品 ReportCatalog を加える。Reporting（保存）・Review（状態の変化）・DuplicateDetection（疑い）の知らせから、一覧の 1 行（ReportListItem）を組み立てて持つ。依頼元・ハンターの一覧は ReportCatalog から読み、詳細と操作は Reporting・Review を正とする。HunterApp が対象地域を読むときは、Reporting が Settings から読んで返す（レビューの R-06）。
- **Consequences** — 良い点: 一覧の絞り込み・並べ替え・ページ分けが 1 か所でできる。書き込みの部品は一覧の形を知らずに済む。悪い点: 一覧は写しで、知らせが届くまでの短い間、詳細より古いことがある。部品が 1 つ増える。
- **Alternatives Rejected** — 画面が 3 つの部品から集めて組み立てる案: ページ分けと絞り込みが同時に効かないため選ばなかった。Review が一覧に必要な項目の写しも持つ案: 確認の決まりの部品に一覧の形が入り、部品の境目があいまいになるため選ばなかった。

## ADR-011: 部品どうしの呼び出しでは利用者の証明をそのまま渡し、知らせは部品からのものだけを受け付ける（レビュー 2 回目の R-10）

- **Context** — ADR-007 で、各部品はログインの証明の役割で操作を許すと決めた。しかし、部品が別の部品をその場で呼ぶとき（Reporting → DuplicateDetection、Reporting → SpeciesDetection など）と、知らせで動く処理（Review が保存の知らせで確認中の記録を作るなど）で、証明をどう扱うかが決まっていなかった。
- **Decision** — ① その場の呼び出し: 呼ぶ側は、画面から受け取った利用者のログインの証明をそのまま渡す。呼ばれた部品も同じ証明で役割を確かめる（例: DuplicateDetection の送信前の問い合わせは、ハンターの証明で許す）。② 知らせ: 利用者の証明は載せず、操作した利用者の ID を載せる。受け手は「MonsterNote の部品が送った知らせだけ」を受け付け、外部から送り込まれた知らせは捨てる。
- **Consequences** — 良い点: 呼び出しの連なりの先でも、操作した人の役割で確かめられる（部品の間で権限が広がらない）。操作の記録に「誰が」を残せる。悪い点: 証明の期限（1 時間）が呼び出しの途中で切れることがある（呼び出しは短いため影響は小さい）。知らせの送り手を確かめる具体の方法は、配置の形によって変わるため NFR Design・Infrastructure Design で決める。**セキュリティ**: 知らせの受け口が外から呼べると、偽の「報告が保存された」で確認中の記録を作られる。受け口を外に出さないことを NFR Design で必ず確かめる。
- **Alternatives Rejected** — 部品どうしの呼び出しは「システム」として特別な証明を使う案: 呼び出しの先で操作した人の役割が分からなくなり、権限が広がるため選ばなかった。知らせにも利用者の証明を載せる案: 知らせはあとで処理されるため証明の期限が切れていることがあり、確かめられないため選ばなかった。

## ADR-012: 一覧の表示名と地名は「報告が保存された」知らせに載せる（レビュー 2 回目の R-09）

- **Context** — ReportCatalog の一覧の行には、ハンターの表示名と捕獲場所の地名がある（ReportListItem の hunterName・placeName）。しかし Report には氏名も地名もなく、どの部品がどの知らせに載せるかが決まっていなかった。
- **Decision** — Reporting は、報告の送信のときに Accounts に同意と従事者番号を確かめる際、ハンターの表示名も受け取り、「報告が保存された」知らせに載せる。地名は、Reporting が保存のときに地図のサービスで緯度・経度から求めて Report に保存し（placeName）、同じ知らせに載せる。地名を求められないときは空にし、一覧では緯度・経度を表示する。
- **Consequences** — 良い点: ReportCatalog はほかの部品を呼ばずに一覧の行を作れる（呼び出しの輪ができない）。地名は報告の時点のものとして残る。悪い点: 表示名をあとで変えても、一覧の古い行は変わらない（試験運用では表示名を変える運用はほぼない）。地図のサービスへの依存が Reporting に加わり、その費用と使い方は Infrastructure Design で確かめる（requirements の OQ-3）。
- **Alternatives Rejected** — ReportCatalog が Accounts と地図のサービスを呼んで補う案: 一覧の部品が外部に依存し、知らせを処理するたびに呼び出しが増えるため選ばなかった。地名を持たず、一覧は緯度・経度だけを表示する案: 依頼元が場所を一目で判断できない（画面案の R2 で地名を表示すると決めた）ため選ばなかった。
