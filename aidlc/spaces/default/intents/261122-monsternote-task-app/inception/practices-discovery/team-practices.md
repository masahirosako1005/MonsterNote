# Team Practices — MonsterNote

## Way of Working

- **Integration branch**: main
- 私たちは**トランクベース開発**で進める。作業は `main` 1 本に集め、長く残る `develop` や `release` のブランチは作らない。
- 作業はすべて作業ブランチで行い、**毎回 GitHub のプルリクエスト（PR）を作り、GitHub の画面で変更内容を確認してから `main` に取り込む**。開発者は 1 人だが、確認の手順を残し、動画教材で PR の画面を見せるためにそうする。[Q1]
- PR の取り込みは GitHub の **「Squash and merge」** で行い、PR ごとに 1 つのコミットにまとめる。`main` の履歴は作業の単位（Construction では Bolt の順）に並ぶ。作業ブランチの細かいコミットは、ブランチを消すまでブランチ側に残る。[Q2][Q14]
- Construction で AI-DLC が作る作業用ブランチ（Bolt ごとのワークツリー）は `main` から作り、PR を通して `main` へ squash で取り込む。まとめたコミットの名前は Bolt の名前にする。
- PR を取り込む前に、CI（GitHub Actions）の検査がすべて通っていることを確かめる。CI が失敗している PR は取り込まない。
- 人が頼んだコミットは、いま居るブランチにそのまま入れる。ブランチを分けるのは、頼まれたときと、上の PR の流れに乗せるときだけにする。
- コミットメッセージと PR のタイトルは、これまでの履歴と同じ Conventional Commits の形（`feat:` `fix:` `docs:` `chore:` `test:` など）にする。
- リポジトリは公開なので、秘密情報（AWS の認証情報、`.env*`、パスワード）はコミットしない。PR を作る前と取り込む前に差分を確かめる（project.md の Forbidden を守るための手順）。

## Walking Skeleton

- 私たちは**最初に「端から端まで一通り動く細い版」（ウォーキングスケルトン）を作る**。[Q15]
- 最初の Unit で通す範囲は **「ログイン → 写真 1 枚の報告 → 依頼元が承認」** とする。Cognito でログインし、ハンターが写真 1 枚付きの報告を送り（写真は S3、記録は DynamoDB）、依頼元が一覧で見て承認する。具体的なサービス構成は Infrastructure Design で決める。
- 種類の判別、重複の検出、交付金の項目などは、スケルトンが動いてから足す（initiative-brief の「価値が先」の順番と同じ）。
- スケルトンは、まず手元のパソコンで単体試験と結合試験の一部を通し、そのあと AWS の `dev` にデプロイして動かして確かめる。[Q15]
- 動いたことの確認は次の 2 段で行う。[Q4]
  - 手元: `npm run verify`（コードの書き方・型・テストをまとめて実行）
  - AWS: 人が確認してから `dev` にデプロイし、`npm run smoke`（画面が開く、API が応答する、ログインできる、などを確かめる）
- AWS へのデプロイは、そのたびに人に確認してから行う（project.md の Mandated）。スケルトンの確認が通り、人が承認してから次の Unit に進む。
- スケルトンの承認後、残りの Construction を「自動で続ける」か「区切りごとに確認する」かは、そのときに選ぶ。

## Testing Posture

- **Methodology**: tdd
- **Methodology evidence**: Q5 で人が「先にテストを書いてから実装する（TDD）」（B）を選んだ。判定ロジックだけを先に書く組み合わせ（C）や、実装のあとで書く形（A）は選ばれなかったため、すべてのテストできる層に同じ順番を当てる。
- **Ordering**: テストできる層（ドメインロジック、Lambda ハンドラ、フロントエンドの部品、CDK スタック）ごとに、先に失敗するテストを書いて実行し、そのテストを通す最小の実装を書き、テストが通ったまま整理する（Red → Green → Refactor）。
- **テストの場所の分け方**: [Q3][Q15]
  - 手元のパソコン: 単体試験と、結合試験の一部。AWS のサービスはモック（代わりの部品）や DynamoDB Local で置き換える。AWS の費用はかからない。
  - AWS の `dev`: 結合試験の残り（ログイン、写真の保存、種類の判別など、本物の AWS サービスを使うもの）と総合試験。デプロイの前には人が確認する。
- **テストの道具**: 単体試験と結合試験は Vitest。CDK は `aws-cdk-lib/assertions` で、作られる構成の中身（`Name=masahiro-<aws-service>-monsternote` のタグ、Lambda のメモリ 128〜256 MB、ログの保存期間 14 日以内、API のスロットリング）を確かめる。E2E は Playwright。
- **カバレッジ**: `feature` スコープの下限どおり **行カバレッジ 80% 以上**。対象は自分で書いたアプリのロジック（画面と API）とし、AWS の構成のコード（CDK）は割合の対象から外す。その代わり、CDK には上の「構成が正しいか」を確かめるテストを必ず書く。[Q6]
- **CI**: GitHub Actions で、push と PR のたびに lint、型チェック、単体・結合テスト（手元と同じモック・DynamoDB Local を使うもの）、カバレッジ、E2E（下記）を動かす。どれかが失敗したら PR を取り込まない。CI は AWS に接続しない。
- **E2E**: [Q7][Q16]
  - push と PR のたびに、CI の中で AWS を使わずに動かす。画面を GitHub Actions の中で起動し、API はモックで置き換える。
  - 本物の AWS を使う E2E は、人の確認のあと `dev` にデプロイしてから動かす。
- **性能**: 無料枠を超えるおそれのある負荷試験はしない。数十リクエスト程度の確認にとどめる（project.md の Forbidden）。
- Test Strategy（Standard）がテストの量と種類を決め、上の下限はそれに足されるだけで、減らすことはない。カバレッジの下限は、テストを通すために下げない。

## Deployment

- AWS の環境は **`dev` の 1 つ**にする。開発と数人の試験運用の両方に使う。費用を抑え、1 人で管理しやすくするため。[Q8]
- デプロイは CDK（TypeScript）で、`ap-northeast-1`、AWS CLI の `default` プロファイルを使い、**人が確認したあと手元のパソコンから `cdk deploy`** で行う。削除（`cdk destroy` など）も同じく、毎回実行前に人に確認する（project.md の Mandated）。[Q9]
- 最初の版では、GitHub Actions からの自動デプロイは入れない。CI は検査だけを行い、AWS の認証情報を GitHub に置かない。将来自動デプロイを入れるときは、OIDC（長期のアクセスキーを置かない）と GitHub Environments の手動承認を組み合わせる。
- org.md の既定「マージしたら staging に自動デプロイ」は、project.md の「デプロイ前に必ず人に確認する」と合わないため、このプロジェクトでは採らない。
- デプロイのあとは `npm run smoke`（画面が開く、API の健康確認、ログインできる）で動いたことを確かめる。スモークが通るまで、デプロイは完了としない。続けて、本物の AWS を使う E2E と総合試験を `dev` で動かす。
- **戻し方**: デプロイのたびに git のタグ（`v0.1.0` など）を付ける。問題があれば、1 つ前のタグをチェックアウトして、人の確認のあと `cdk deploy` し直す。DynamoDB のデータが消える変更（テーブルの作り直しなど）は、事前に人に確認する。[Q10]
- 新しい AWS リソースを作る前に、無料枠に収まるかと想定の月額を示す。すべてのリソースに `Name=masahiro-<aws-service>-monsternote` のタグを付ける。常時課金のサービスは使わず、mononoke のリソースには触れない（project.md）。
- 費用の見張りには、共用アカウントの既存の AWS Budgets を使い、MonsterNote の費用はタグ別に請求コンソールで確かめる。

## Code Style

- 言語は TypeScript 5.x に統一し、`strict` を有効にする。
- リポジトリは 1 つとし、中を画面（`frontend`）・API（`backend`）・AWS の構成（`infra`）の 3 つに分けて、npm workspaces でまとめて管理する。[Q11]
- 整形は **Prettier**、静的検査は **ESLint**（typescript-eslint）。設定はリポジトリのルートに置き、CI で実行して、失敗した PR は取り込まない。
- 名前の付け方は TypeScript の慣習どおり（変数・関数は camelCase、型・クラス・React コンポーネントは PascalCase、定数は UPPER_SNAKE_CASE）。
- **言語**: コードの名前（識別子）は英語、コードのコメントは日本語、利用者に見せる画面の文字は日本語にする。コメントを日本語にするのは、動画教材で読みやすくするため。[Q12]
- エージェントがスタイルの指摘をするときは、まず ESLint・Prettier の設定を読み、それで扱われていない点だけを指摘する。
