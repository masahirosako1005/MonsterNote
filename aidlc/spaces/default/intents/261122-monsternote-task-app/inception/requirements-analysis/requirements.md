# Requirements — MonsterNote 最初の版（試験運用）

入力: `ideation/intent-capture/intent-statement.md`（intent-statement）、`ideation/scope-definition/scope-document.md`（scope-document）・`intent-backlog.md`、`ideation/feasibility/constraint-register.md`・`raid-log.md`、`ideation/rough-mockups/wireframes.md`・`user-flow.md`、`ideation/approval-handoff/initiative-brief.md`、`inception/practices-discovery/team-practices.md`（team-practices）、requirements-analysis-questions.md（Q1〜Q12）。

最初の依頼文は「数人で使うタスク管理 Web アプリ」だったが、Intent Capture の Q9 で「害獣ハンターの報告アプリ」が正しいと確定している。 [desc]

各要件の「出典」は、その要件のもとになった決定を示す（F 番号は intent-backlog の機能、RQ は本ステージの質問、IC は Intent Capture、RM は Rough Mockups の質問）。

## 1. 意図の分析

| 項目 | 内容 |
|---|---|
| 目的 | 害獣を捕獲・駆除したハンターが写真付きで報告し、依頼元（市町村の担当課・猟友会）が確認する流れを、1 か月以内に試験運用できる状態にする |
| 一番の課題 | 同じ個体を何度も報告して賞金を二重に受け取る不正を見つける |
| 利用者 | ハンター（高齢の人が多い）、依頼元（市町村の担当課・猟友会）、管理者（開発者本人） |
| 種類 | 新しいアプリ（Greenfield）。画面・API・AWS の構成を含む、複数の部品にまたがる |
| 成功の判定 | ① ハンター 3 人以上が各 1 件以上を写真付きで報告し、依頼元がすべて確認 ② 同じ個体を 2 回報告したテストで重複の疑いが見つかる ③ MonsterNote の AWS 費用が月 100 円以内（scope-document） |

## 2. 機能要件（Functional Requirements）

### FR1. アカウントとログイン（F1）

- **FR1.1** 管理者は、ハンターと依頼元のアカウントを作成し、招待できる。ハンター・依頼元が自分でアカウントを作る画面は設けない。（RQ Q2）
  - Given 管理者がハンターのアカウントを作成した When 招待されたハンターが初めてログインする Then 同意の画面が表示される
- **FR1.2** 利用者は、ID とパスワードでログインできる。ID かパスワードが違うときは、ログインできず「ID かパスワードが違います」と表示する。（wireframes H1・R1）
- **FR1.3** アカウントには役割（ハンター／依頼元／管理者）があり、役割ごとに使える画面と操作を分ける。依頼元には所属（市町村の担当課／猟友会）を記録する。（RQ Q1、constraint-register C-S2）
- **FR1.4** ハンターは初回のログインで、報告の氏名・位置・写真を依頼元に見せることへの同意を求められる。「同意しない」を選んだハンターは報告を作れず、理由と問い合わせ先が表示される。同意した日時を記録する。（F1、constraint-register C-R4、wireframes H1）
- **FR1.5** ハンターは初回のログインで、捕獲従事者の番号を登録する。番号が空のままでは先に進めない。（F1、C-R3）
- **FR1.6** ログインの状態は、最後に使ってから 30 日間保つ（毎回 ID とパスワードを入れなくてよい）。30 日使わなかったとき、またはアカウントが無効になったときは、ログイン画面に移る。報告の作成中にログインが切れた場合、作成中の内容は失われてよい（下書きを残さないため。FR2.9）が、そのことを画面に表示する。（corner checklist: セッション切れ ／ 仮定 A-8）
- **FR1.8** 管理者がアカウントを作るときは、仮のパスワードを発行する。仮のパスワードは、管理者がアプリの外（手渡しの紙など）で本人に渡す。初めてのログインでは、新しいパスワードへの変更を求める。パスワードは 8 文字以上で、英字と数字を両方含む。（R-04 ／ 仮定 A-9）
- **FR1.7** ハンターと依頼元は、メニューからログアウトできる。（wireframes 全体の方針）

### FR2. 写真付きの報告（F2）

- **FR2.1** ハンターは、ホームの「報告する」から、1 画面に 1 項目ずつ順番に報告を作る。順番は「全身の写真 → 尻尾の写真 → 種類の確認 →（クマのときだけ）胸の写真 → 雌雄の選択 → 成獣／幼獣の選択 → 捕獲の方法の選択 → 内容の確認と送信」。ステップの数は通常 7、クマのときは 8 と表示する。各画面に「戻る」がある。（RM Q2・Q8、wireframes H3〜H6、RQ Q4、R-01）
- **FR2.13** クマの胸の写真は、撮るよう案内するが必須ではない。「撮れなかった」のボタンで先に進める。その場合は報告に「胸の写真なし」と記録し、月の輪による照合（FR12）は行わない。（R-08）
- **FR2.2** 写真は、その場でカメラで撮ることも、端末に保存済みの写真から選ぶこともできる。（RQ Q3）
- **FR2.3** 写真に撮影日時と位置（緯度・経度）の情報があるときは、報告の捕獲日時と捕獲場所に自動で入れる。全身の写真の情報を使い、全身の写真にない項目は尻尾の写真の情報を使う。写真の情報は、写真を縮小する前に読み取る。（F2、RQ Q11、R-07）
- **FR2.14** 捕獲日時と捕獲場所は、自動で入った値にも手で入れた値にも、次の確認を行う。満たさないときは理由を表示し、送信できない。（R-03 ／ 仮定 A-10）
  - 捕獲日時は、送信の時刻より後（5 分の誤差を許す）であってはならず、送信の時刻から 7 日より前であってはならない
  - 捕獲場所は、管理者が設定した対象地域（中心の地点と半径。初期値は日本の範囲: 北緯 20〜46 度・東経 122〜154 度）の中でなければならない
  - Given 9 日前に撮った写真を選んだ When 内容の確認の画面を開く Then 「捕獲日時が 7 日より前です」と表示され、送信ボタンは押せない
- **FR2.4** 写真に撮影日時または位置の情報がないときは、その欄を空白で表示し、ハンターが手で入力する。日時は日付と時刻を選んで入力し、位置は地図上で場所を指して入力する。空白のままでは送信できない。（RQ Q11）
  - Given 位置情報のない写真を選んだ When 内容の確認の画面を開く Then 捕獲場所の欄は空白で、地図で指すよう案内が表示され、送信ボタンは押せない
- **FR2.5** 日時または位置を手で入力した報告には「日時・位置は手入力」の印を付け、依頼元の一覧と詳細に表示する。（RQ Q11 の補い）
- **FR2.6** 写真ごとに、何をどう撮るかを文字と例の図で案内する（全身はマーキングが写るように、尻尾、クマの胸は月の輪が写るように）。（F2、constraint-register C-R1、RM Q3・Q8）
- **FR2.7** 内容の確認の画面では、写真・捕獲日時・捕獲場所・種類・成獣／幼獣・雌雄・捕獲の方法・従事者番号を一覧で表示し、各項目の画面に戻って直せる。（wireframes H6）
- **FR2.8** 「送る」を押してから送信が終わるまで、ボタンを押せない状態にし、「確認しています」と表示する。同じ報告が 2 件作られることはない。（wireframes H6、corner checklist: 二重送信）
- **FR2.9** 下書きは残さない。報告の作成をやめるとき（「送るのをやめる」や、作成の途中でホームに戻るとき）は「写真と入力内容は消えます。よろしいですか？」と確かめ、「消す」を選んだら内容を消す。（RQ Q7・Q12）
- **FR2.10** 送信に失敗したときは、入力した内容と写真を画面に残したまま「送れませんでした」と「もう一度」ボタンを表示する。（user-flow のエラーの流れ）
- **FR2.11** 送信が終わったら送信完了の画面を表示し、ホームの一覧に「確認中」で表示する。（user-flow の成功）
- **FR2.12** 写真として受け付けるのは画像ファイル（JPEG・PNG・HEIC）だけで、選ぶ時点で 1 枚 15 MB までとする。それ以外は理由を表示して選び直してもらう。受け付けた写真は、送る前に端末で長辺 2,048 ピクセルの JPEG に縮小してから送る（HEIC もこのとき JPEG に変える）。JPEG に変えられない写真は、理由を表示して選び直してもらう。（corner checklist: 不正な入力、R-07 ／ 仮定 A-4）

### FR3. 種類の判別と修正（F3）

- **FR3.1** 全身の写真から種類（クマ・イノシシ・シカ）を自動で判別する。3 種類のうち確からしさ（確信度）が最も高いものが 80% 以上なら「判別できた」とし、種類の確認の画面でその種類を選んだ状態で、「AI の判定」と確からしさを添えて表示する。80% 未満なら「判別できなかった」とする（FR3.3）。ハンターが「次へ」を押すまで種類は確定しない。（F3、IC Q19、R-02 ／ 仮定 A-7）
- **FR3.5** 判別の精度は、3 種類それぞれ 10 枚以上の捕獲後の写真（合計 30 枚以上）で確かめ、「判別できた」とした写真の 70% 以上で種類が正しいことを目標とする。目標に届かなくても、ハンターが直せるため報告は作れる。結果は Build and Test で記録する。（R-02 ／ 仮定 A-7）
- **FR3.2** ハンターは、判別の結果を大きなボタンで別の種類に直せる。（F3、IC Q12）
- **FR3.3** 判別できなかったとき、または判別に失敗したときは、何も選ばれていない状態で表示し、ハンターが手で選ぶ。報告の作成は止まらない。（user-flow のエラーの流れ）
- **FR3.4** 報告には、自動判別の結果（判別できなかった場合はそのこと）と、ハンターが最終的に選んだ種類の両方を記録する。（依頼元が直された報告を見分けるため）

### FR4. 雌雄の記録（F4）

- **FR4.1** ハンターは、雌雄を「オス」「メス」「不明」の大きなボタンで選ぶ。選ばないと次に進めない。（F4、scope-document）

### FR5. 交付金の実績報告に使う項目（F13）

- **FR5.1** 報告には次の項目を記録する: 捕獲日時、捕獲場所（緯度・経度）、種類、成獣／幼獣、雌雄、捕獲の方法（わな／銃／その他）、捕獲従事者の番号、写真（全身・尻尾、クマのときは胸）。（RQ Q4）
- **FR5.2** 成獣／幼獣と捕獲の方法は、それぞれ別の画面で、ハンターが大きなボタンで選ぶ（成獣／幼獣は「成獣」「幼獣」の 2 個、捕獲の方法は「わな」「銃」「その他」の 3 個。どちらも NFR7 の 1〜3 個に収まる）。選ばないと次に進めない。これは画面案にない 2 画面の追加で、画面への反映は User Stories・Refined Mockups で行う。（RQ Q4、R-01）
- **FR5.3** 項目の書式は、国の最新のマニュアルで確かめるまで仮とする（Open questions の OQ-1）。

### FR6. 重複の疑いの検出（F6）

- **FR6.1** 「送る」を押したとき、すでにある報告（自分と他のハンターの報告。却下されたものを除く）の中に、同じ種類で、捕獲場所が半径 1 km 以内、かつ捕獲日時の差が 24 時間以内のものがあれば「重複の疑い」とする。（F6、RQ Q5）
  - Given イノシシの報告 A（11/20 10:00、地点 P）がある When 11/21 9:00 に、地点 P から 800 m の地点でイノシシの報告 B を送る Then B は重複の疑いになる
  - Given 同じ報告 A がある When 11/21 11:00（25 時間後）に同じ地点でイノシシの報告 C を送る Then C は重複の疑いにならない
  - Given 同じ報告 A がある When 同じ時刻・同じ地点でシカの報告 D を送る Then D は重複の疑いにならない（種類が違う）
- **FR6.2** 距離と時間の基準は境界を含む（ちょうど 1 km、ちょうど 24 時間は重複の疑いとする）。距離は 2 地点の緯度・経度から地球を球とみなして計算した地表の距離（大円距離、地球の半径 6,371 km）とし、テストでは 1 m の誤差を許す。（R-06）
- **FR6.4** 報告を保存したあとにも、同じ基準でもう一度確かめる。ほぼ同時に送られた 2 件が互いに重複の疑いに当たるときは、両方に「重複の疑い」の印を付ける（ハンターへの送信前の知らせ〈FR7〉は行わない）。また、重複の疑いの相手になった既存の報告にも、同じ印を付ける。（R-06）
- **FR6.3** 基準（距離・時間）は管理者が設定で変えられる。変えた基準は、変えたあとに送られる報告から使う。（RQ Q5）

### FR7. 送信前にハンターへ知らせる（F9）

- **FR7.1** 重複の疑いがあるときは、送信する前に「近くで同じ日に、よく似た報告があります。同じ個体ではありませんか？」と表示し、「別の個体なので送る」と「送るのをやめる」のボタンを出す。似ている報告の、他のハンターの氏名や写真は見せない（種類・日時・おおよその距離だけを見せる）。（RM Q7、wireframes H7、constraint-register C-S2）
- **FR7.2** 「別の個体なので送る」を選んだら送信し、その報告に「重複の疑い」の印を付け、依頼元に似ている報告と並べて見せる。（RM Q7）
- **FR7.3** 「送るのをやめる」を選んだら、FR2.9 の確認のうえで内容を消し、ホームに戻る。（RQ Q12）

### FR8. 依頼元による確認（F10）

- **FR8.1** 依頼元（市町村の担当課・猟友会のどちらの所属でも）は、すべてのハンターのすべての報告を一覧で見られる。一覧は新しい順に並び、「確認中」「承認」「却下」「重複の疑い」「手入力」で絞り込める。（RQ Q1、wireframes R2）
- **FR8.2** 一覧は 1 ページ 50 件までとし、それより多いときはページを分ける。報告がないときは「報告はまだありません」と表示する。（corner checklist: 一覧）
- **FR8.3** 依頼元は報告の詳細で、写真・すべての項目・自動判別の結果・印（重複の疑い・手入力）を見られる。重複の疑いがある報告では、似ている報告を並べて見比べられる。（wireframes R3）
- **FR8.4** 依頼元は、確認中の報告を承認または却下できる。却下では理由を「重複の疑い」「写真が不十分」「対象の地域・種類ではない」「その他」から選び、「その他」では理由を書く（空のままでは却下できない）。（RQ Q6）
- **FR8.5** 承認・却下は、サーバーが受け付けた時点で確定する。確定から 10 秒間は、操作した本人だけが「取り消す」で「確認中」に戻せる。10 秒を過ぎると取り消せない。（user-flow の依頼元のエラーの流れ、R-05 ／ 仮定 A-11）
- **FR8.6** 承認・却下は、報告が「確認中」のときだけサーバーが受け付ける。2 人の依頼元が同じ報告を操作したときは、サーバーが先に受け付けた操作だけが有効になり、あとの操作は受け付けず「すでに確認済みです（承認／却下、確認した人）」と表示する。取り消しの 10 秒間も報告は確認済みとして扱い、他の人の操作は受け付けない。取り消されて「確認中」に戻ったあとは、誰でも操作できる。（RQ Q1、corner checklist: 同時の操作、R-05）
- **FR8.7** 承認・却下した人と日時を記録し、詳細に表示する。

### FR9. ハンターの報告の一覧と状態

- **FR9.1** ハンターはホームで、自分の報告だけを新しい順に一覧で見られる（日付・種類・状態）。状態は文字とアイコンで示す（確認中・承認・却下）。（wireframes H2）
- **FR9.2** ハンターは自分の報告の詳細で、状態と、却下のときは理由を見られる。却下の報告からは「撮り直して新しく報告する」で新しい報告を作れる。（wireframes H9）
- **FR9.3** 「確認中」の報告には「送ってから n 日」を表示する。送ってから 7 日を過ぎても確認中のときは、ハンターに「依頼元の確認に時間がかかっています。急ぐときは依頼元に連絡してください」と表示し、依頼元の一覧ではその報告に印を付ける。アプリからの催促・通知はしない。（RQ Q10、wireframes H2）
- **FR9.4** ハンターは、他のハンターの報告を一覧でも詳細でも見られない（API でも取得できない）。（constraint-register C-S2）

### FR10. 管理者の操作

- **FR10.1** 管理者は、アカウントの作成（FR1.8）・無効化、パスワードの再設定、重複の基準の変更（FR6.3）、対象地域の設定（FR2.14）ができる。（RQ Q2・Q5、R-04）
- **FR10.3** パスワードの再設定では、管理者が新しい仮のパスワードを発行し、アプリの外で本人に渡す。本人は次のログインで変更を求められる。（R-04）
- **FR10.4** 無効にしたアカウントでは、ログインできない。ログイン中だった場合も、1 時間以内に操作できなくなる。そのアカウントが送った報告と、確認した記録は残る。管理者は無効にしたアカウントを有効に戻せる。（R-04 ／ 仮定 A-8）
- **FR10.5** ハンターが同意を取り消したいときは、管理者に連絡する。管理者はそのアカウントを無効にする（FR10.4）。それまでの報告は、試験運用が終わるときに削除する（FR10.2）。アプリの中で同意を取り消す画面は設けない。（R-08）
- **FR10.2** 試験運用が終わったら、管理者の確認のあと、すべての報告と写真を削除できる。削除の前に、削除する件数を表示して確かめる。（RQ Q8）

### FR11. 写真による重複の疑い（F7・Should）

- **FR11.1** 送られた写真が、すでにある報告の写真と同じ、またはほぼ同じときは「重複の疑い（写真）」とし、FR7・FR8 と同じように扱う。Must の要件がすべて終わったあとに作る。（F7、scope-document）

### FR12. クマの月の輪による照合（F8・Should）

- **FR12.1** クマの報告で、胸の写真の月の輪の形が、すでにあるクマの報告と似ているときは「重複の疑い（月の輪）」として依頼元に知らせる。実現性が低いため、Must と FR11 のあとに挑戦し、間に合わなければ次の版に回す。（F8、scope-document）

## 3. 非機能要件（Non-Functional Requirements）

- **NFR1 費用**: MonsterNote のタグが付いた AWS 費用が月 100 円以内（写真の自動判別を含む）。請求コンソールのタグ別の表示で毎月確認する。（C-C1・C-C2）
- **NFR2 応答時間**: 試験運用の規模（同時の利用者 10 人以下）で、一覧・詳細の表示は 95% のリクエストで 3 秒以内。送信（写真を除く）から送信完了の表示までは 95% で 10 秒以内（重複の判定と種類の判別を含む）。写真のアップロードは、縮小後の写真（FR2.12）1 枚につき、4G 回線で 5 秒以内を目安とする。（仮定 A-3、R-07）
- **NFR3 規模**: 報告は月 50 件未満、写真は月 150 枚程度、利用者は 20 人以下を前提とする。（raid-log A1）
- **NFR4 認証と認可**: すべての API は認証を必要とする。ハンターは自分の報告だけ、依頼元はすべての報告を読める。承認・却下は依頼元だけ、アカウントと設定の操作は管理者だけができる。画面で隠すだけでなく、API でも同じ確認をする。（C-S2）
- **NFR5 データの保護**: 通信は HTTPS だけを使う。保存する報告と写真は暗号化する。写真は認証された利用者にだけ、期限付きの URL で見せる。氏名・位置・従事者番号はログに出さない。（C-S1・C-S2）
- **NFR6 秘密情報**: AWS の認証情報・パスワードなどはリポジトリに置かない。（C-S1）
- **NFR7 アクセシビリティ（ハンター側）**: 文字 20px 以上、ボタンの高さ 64px 以上で画面幅いっぱい、ボタンの間隔 16px 以上。色だけで意味を伝えない。文字のコントラスト比 4.5:1 以上（WCAG 2.1 AA）。報告の作成の各画面の大きなボタンは 1〜3 個。（RM Q5、wireframes）
- **NFR8 デザイン**: Google のマテリアルデザインに沿う。画面の文字は日本語。（RM Q6、team-practices）
- **NFR9 対応する機器**: ハンターは iPhone の Safari と Android の Chrome（それぞれ最新とその 1 つ前の版）、縦向き。依頼元はパソコンの Chrome と Edge（最新版）とスマホ（ハンターと同じブラウザ）。対象外のブラウザでは、対応するブラウザを案内する。（RQ Q9、RM Q4）
- **NFR10 可用性**: 試験運用の期間中、AWS のサーバレスのサービスの通常の可用性に従う（独自の目標は設けない）。障害で送れなかった報告は、FR2.10 で入力内容を残して送り直せる。（仮定 A-5）
- **NFR11 保存期間**: 報告と写真は試験運用が終わるまで保存し、終了後に管理者の確認のうえで削除する（FR10.2）。ログの保存期間は 14 日以内。（RQ Q8、C-T3）
- **NFR12 運用の制約**: API にスロットリングを設定し、関数のメモリは 128〜256 MB とする。常時起動・時間課金のリソースは使わない。すべてのリソースに `Name=masahiro-<aws-service>-monsternote` のタグを付ける。（C-T2・C-T3、project.md）
- **NFR13 品質**: 画面と API のロジックの行カバレッジ 80% 以上。テストは先に書く（TDD）。push と PR のたびに CI で lint・型チェック・テスト・E2E（AWS なし）を動かす。（team-practices）
- **NFR14 監査の記録**: 報告の送信、承認・却下、取り消し、アカウントの作成・無効化・パスワードの再設定、基準・対象地域の変更、データの削除について、誰が・いつ・何をしたかを記録する。監査の記録はアプリのデータとして報告と同じ場所に保存し、報告と同じく試験運用が終わるまで保存する。NFR11 の「ログの保存期間 14 日以内」は、AWS の動作ログ（CloudWatch Logs）に当てはめ、監査の記録には当てはめない。（corner checklist: 重要な操作の記録、R-07）

## 4. 制約

- 技術・費用・組織・規制・セキュリティの制約は `ideation/feasibility/constraint-register.md` の C-T1〜C-T5、C-C1〜C-C4、C-O1〜C-O5、C-R1〜C-R4、C-S1〜C-S2 に従う。
- 開発の進め方（PR と Squash and merge、TDD、AWS の環境は dev の 1 つ、人の確認のあと手元からデプロイ）は team-practices に従う。
- 最初の版は 1 か月以内（C-O2）。

## 5. 仮定

| ID | 仮定 | 理由 | 確かめる人・時期 |
|---|---|---|---|
| A-1 | 依頼元の 2 組織は、互いの承認・却下を受け入れる（どちらが確認してもよい） | Q1 の回答 | 開発者・試験運用の前に依頼元へ説明するとき |
| A-2 | 保存済みの写真を選べるため、写真の使い回しや、日時・位置を少しずらして重複の検出を避けることは、アプリだけでは防げない。FR2.14 の確認で明らかな不正を止め、残りは依頼元が「手入力」の印・写真・マーキング・尻尾の現物を見て判断する。この回避は成功の判定②では確かめず、試験運用のあとに依頼元の意見で見直す | Q3・Q11 の回答、R-03 | 開発者・試験運用のあと |
| A-3 | 応答時間（NFR2）の値は、試験運用の規模とスマホの回線を想定した目安 | 業務の要件がないため | 開発者・Build and Test |
| A-4 | 写真の大きさの上限 15 MB は、スマホのカメラの写真が収まる大きさとして設定 | スマホの写真は通常 2〜8 MB | 開発者・試験運用 |
| A-5 | 試験運用では独自の可用性の目標を設けない | 数人の試験運用で、紙の報告に戻れるため | 開発者 |
| A-6 | スマホのブラウザは、写真の撮影日時・位置の情報を消すことがある。その場合は FR2.4 の手入力になる | ブラウザの仕様による | 開発者・最初の細い版で実機確認 |
| A-7 | 種類の判別の「80% 以上で判別できた」と「正答率 70% 以上」は初期値。試験用の写真で確かめ、必要なら管理者が変えられるようにする | 捕獲後の写真での精度が未確認（raid-log R3・A2） | 開発者・Build and Test |
| A-8 | ログインを 30 日保ち、無効化を 1 時間以内に反映する | 高齢のハンターが毎回パスワードを入れなくて済むように。1 時間は、ログインの確認に使う鍵の有効期限 | 開発者・Infrastructure Design |
| A-9 | 仮のパスワードの手渡しと、8 文字以上・英字と数字を含む規則 | 管理者がアカウントを作る運用（RQ Q2）で、メールを使わない | 開発者・試験運用の前 |
| A-10 | 捕獲日時は 7 日前まで、対象地域の初期値は日本の範囲 | 報告は捕獲から間もなく出す前提。試験運用の市町村が決まったら、管理者が対象地域を設定する | 開発者・依頼元に説明するとき |
| A-11 | 取り消しの猶予は 10 秒 | 押し間違いに気づくのに足りる長さとして設定 | 開発者・試験運用 |
| A-12 | 写真の縮小（長辺 2,048 ピクセル）で、マーキングや尻尾の確認に必要な細かさは保たれる | スマホの画面やパソコンで見るには十分な大きさ | 開発者・最初の細い版で確認 |
