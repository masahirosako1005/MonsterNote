# Performance Requirements（性能と画面の要件）— U2 `u2-report-duplicate`

入力: `construction/u1-skeleton/nfr-requirements/performance-requirements.md`（U1 の NFR2.1〜NFR2.5・NFR7.1〜NFR9.2。U2 はこれを引き継ぐ）、`construction/u2-report-duplicate/functional-design/`（functional-spec・rules・frontend-components）、`inception/requirements-analysis/requirements.md`（NFR2・NFR7・NFR8・NFR9）、`inception/contract-design/contract-summary.md`（2.3 の時間切れとやり直し）、nfr-requirements-questions.md（Q1〜Q6）。

前提の規模: 同時の利用者 10 人以下、報告は月 50 件未満、写真は月 150 枚程度（NFR3）。U1 で決めた応答時間（一覧 3 秒・送信 10 秒）は U2 でも守る。

## 1. 応答時間（U2 で足すもの）

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR2.6 | 写真の受け付け（`POST /v1/photos`）は、95% のリクエストで 3 秒以内（署名付きの URL を返すだけ） | API Gateway の Latency の p95 | NFR2 |
| NFR2.7 | アップロードの完了（`POST /v1/photos/{id}/complete`）は、全身の写真で 95% のリクエストで **6 秒以内**（下の内訳。関数の起動の遅れを含む）。全身以外は 3 秒以内 | 同上 | NFR2、Q1、レビュー R-03 |
| NFR2.8 | 種類の判別は **3 秒で区切る**。超えたら「判別できなかった」として返し、報告の作成は止めない | 単体試験（時刻を進めて確かめる）、dev での計測 | Q1、BR6.3 |
| NFR2.9 | 送信の前の重複の問い合わせ（`POST /internal/v1/duplicate-checks`）は **2 秒で区切る**（contract-summary 2.3 の内部の呼び出しと同じ） | 単体試験、dev での計測 | Q3、contract-summary 2.3 |
| NFR2.10 | 保存のあとの重複の判定（`report.saved` の受け手）は、**10 秒以内**に終わる（知らせの受け手の時間の予算） | 関数の Duration の最大 | NFR2、U1 の monitoring-design |
| NFR2.11 | 写真のアップロード（縮小後 1 MB 前後）は 1 枚あたり 4G の回線で 5 秒以内を目安とする。2〜3 枚を順に送るため、全身・尻尾の 2 枚で 10 秒前後になる | 画面での計測（dev） | NFR2、NFR2.4 |

### アップロードの完了の 6 秒（NFR2.7）の内訳

| 処理 | 見込み | 備考 |
|---|---|---|
| 関数の起動の遅れ（コールドスタート） | 1.5 秒以内 | Node.js 22 Arm、小さな束。U1 の NFR2.5 の決まりを守る |
| 写真の実物の確認（大きさ・形式） | 0.3 秒以内 | 保存場所への問い合わせ 1 回 |
| 種類の判別（外部のサービス） | 3 秒で区切る | NFR2.8 |
| 記録の書き込みとやりとり | 1 秒以内 | — |
| **合計（最悪）** | **約 5.8 秒** | 6 秒の予算に収まる |

判別の 3 秒（NFR2.8）だけで予算を使い切らないよう、起動の遅れの分を見込んで 6 秒にした（レビュー R-03）。dev で測って 6 秒に届かなければ、判別の区切りを縮める。

### 送信の 10 秒（NFR2.2）の内訳

| 処理 | 見込み | 備考 |
|---|---|---|
| 送信のキーの確認 | 0.1 秒以内 | 条件にした 1 回の書き込み |
| 報告できるハンターかの確認（C10） | 2 秒で区切る | contract-summary 2.3 |
| 写真の確認（2〜3 枚） | 0.5 秒以内 | 記録を読むだけ |
| 日時・場所の確認（設定の読み出しを含む） | 2 秒で区切る | C11 |
| 重複の問い合わせ（C9） | 2 秒で区切る | NFR2.9 |
| 保存と知らせの送信 | 1 秒以内 | — |
| **合計（最悪）** | **約 8 秒** | 10 秒の予算に収まる |

種類の判別は、写真のアップロードのとき（NFR2.7）に終わっているため、送信には含まれない。

## 2. 画面の要件（U2 で足すもの）

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR7.2 | 報告の作成の各画面の大きなボタンは 1〜3 個（種類 3・雌雄 3・成獣／幼獣 2・捕獲の方法 3）。ボタンは 64px 以上・画面幅いっぱい・間隔 16px 以上 | E2E（Playwright）で寸法を確かめる | NFR7 |
| NFR7.3 | 地図で場所を指す部品は、キーボードでも緯度・経度を直接入れられる手段を併せて置く（地図だけに頼らない） | E2E（キーボード操作）、axe | NFR7、frontend-components |
| NFR7.4 | 「判別しています」の表示は 3 秒まで。超えたら「判別できませんでした。手で選んでください」に変える（待たされている感じを残さない） | E2E | Q1、NFR7 |
| NFR9.3 | 写真の縮小（長辺 2,048 px の JPEG）と撮影情報の読み取りは、対応する機器（NFR9）のブラウザの機能だけで行う。縮小は 1 枚あたり 3 秒以内を目安とする | 実機での確認（dev） | NFR9、FR2.12 |
| NFR9.4 | ハンター用の画面のファイル（ビルド後）は、U2 で地図の部品が増えても 800 KB 以下（圧縮後）を目安とする。超えたら、地図は必要な画面でだけ読み込む | ビルドの結果の大きさ | NFR2・NFR9、U1 の NFR9.2 |

## Assumptions & Open Questions

- NFR2.7 の 6 秒は上の内訳のとおり。U1 の NFR2.5（起動の遅れを含めても目標を守る。常時起動の設定は使わない）を守るため、起動の遅れ 1.5 秒を見込んでいる。 [assumption]
- NFR9.4 の 800 KB は、U1 の 500 KB に地図の部品の分を足した目安。地図の部品の選定は Code Generation で行う。 [assumption]
- 送信の内訳の「合計（最悪）」は、すべての内部の呼び出しが時間切れ寸前まで掛かった場合。普通は 2 秒以内に収まる見込み。 [assumption]
