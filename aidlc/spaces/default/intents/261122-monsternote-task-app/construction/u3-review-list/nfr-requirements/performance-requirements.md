# Performance Requirements（性能と画面の要件）— U3 `u3-review-list`

入力: `construction/u1-skeleton/nfr-requirements/performance-requirements.md`（U1 の NFR2.1〜NFR9.2。U3 はこれを引き継ぐ）、`construction/u3-review-list/functional-design/`（functional-spec・rules・frontend-components）、`inception/requirements-analysis/requirements.md`（NFR2・NFR7・NFR9）、nfr-requirements-questions.md（Q1〜Q4）。

前提の規模: 同時の利用者 10 人以下、報告は月 50 件未満（NFR3）。U1 で決めた応答時間（一覧・詳細 3 秒、承認 3 秒）は、絞り込みがあっても同じ目標を守る（Q1）。

## 1. 応答時間（U3 で足すもの）

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR2.12 | **絞り込みを掛けた一覧（`GET /v1/catalog/reports`）も、95% のリクエストで 3 秒以内。** 条件に合う行を最後まで数えても（上限 2,000 件）、この目標を守る | API Gateway の Latency の p95（絞り込みあり・なしの両方で測る） | NFR2、Q1 |
| NFR2.13 | 却下（`PUT /v1/reviews/{id}/decision`、decision=rejected）は、95% のリクエストで 3 秒以内（承認と同じ目標。BR3.8 の確認を含む） | 同上 | NFR2、U1 の NFR2.3 |
| NFR2.14 | 取り消し（`POST /v1/reviews/{id}/decision/undo`）は、95% のリクエストで 2 秒以内（条件にした 1 回の書き換えだけなので承認より速い） | 同上 | NFR2 |

## 2. 絞り込みの読み出しの見込み

| 項目 | 見込み（最良〜最悪） |
|---|---|
| 1 回の読み出しで取れる行数 | DynamoDB のクエリ 1 回あたり 100 件程度（1 MB の制限、行は小さい） |
| 2,000 件を読むのに要る回数 | 20 回ほど |
| 1 回あたりの時間 | 10〜80 ミリ秒（コールドスタートを含まない） |
| 2,000 件の読み出しの合計時間 | 0.2〜1.6 秒（最悪でも 3 秒の予算に収まる） |
| 試験運用の規模での実際の件数 | 月 50 件未満なので、1 ページ（50 件）で収まり、上限（2,000 件）には遠く届かない |

最悪値（1.6 秒）に、関数の起動の遅れ（NFR2.5）と API Gateway のオーバーヘッドを足しても 3 秒の予算には収まる見込みだが、**この見積もりは暫定で、dev の実測で確定する**（レビュー R-05）。実測で割り込んだときは、先に関数のメモリを引き上げて様子を見て、それでも届かなければ読む上限（2,000 件）を下げる（NFR12.9）。独自のキャッシュは置かない（データの新しさを優先する。NFR5 の観点とも合う）。

## 3. 画面の要件（U3 で足すもの）

| ID | 要件 | 測り方 | 出典 |
|---|---|---|---|
| NFR7.5 | 「取り消す」の残り時間の表示は、**サーバーが返した期限の時刻と、画面が受け取った時刻の差**から求める。画面の時計の絶対値（`Date.now()` だけ）に頼らない | 単体試験（画面の時計をずらしても正しい秒数を表示する） | Q2、BR3.9 |
| NFR7.6 | 絞り込みの選択（状態・印）は 64px 以上のボタンで、複数選べることが見て分かる形にする（チェックの印など） | E2E（Playwright）で寸法を確かめる | NFR7 |
| NFR7.7 | 同時の操作で弾かれた画面は、エラーの赤い表示にせず、状態を出し直す形にする（押し間違いではないため） | E2E、axe | Q3、frontend-components |

## Assumptions & Open Questions

- NFR2.12 の見積もりは DynamoDB の一般的な性能からの見込みで、最悪値でも 3 秒に収まる計算だが確定ではない。dev で実測し、届かなければまずメモリを引き上げ、それでも届かなければ上限を下げる（NFR12.9、Q1 のとおり。レビュー R-02・R-05）。 [assumption]
- NFR7.5 の「受け取った時刻」は、応答が返ってきた時点の画面の時計。通信の遅れ（数百ミリ秒）の分だけ実際の残り時間より短く見えることがあるが、受け付けの判断はサーバーが行うため実害はない。 [assumption]
