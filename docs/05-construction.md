# 05. Construction（作る）

## ゴール

Inception で決めた設計と計画にしたがって、Unit（作る単位）ごとに詳細設計・コード・テストを作り、AWS の dev 環境で動かす。この章でも、各ステージの質問・回答・承認の判断を記録する。

## 記録の読み方

- **AI の質問** … AI-DLC が作った質問ファイルや、チャットで出した選択肢
- **回答** … 自分が選んだ答え（質問ファイルを直接編集）
- **承認ゲート** … ステージが終わったときの判断（Approve / Request Changes など）と、その理由

## 0. Construction の始まり

### AI の質問: 誰が作るか
「Inception が終わり、計画には Unit が 4 つあります。誰が作りますか？」

### 回答: **Just me**（このセッションが、ステージごとに Unit を作る）

### 最初の細い版（walking skeleton）の扱い
AI-DLC は、チームのルール（team.md の Walking Skeleton）を読み、「最初に細い版を作る」チームであることを確認した（skeleton stance: on）。そのため、Delivery Planning で「ステージごとに進める」と決めていても、**最初の Unit（U1 細い版）だけは、設計からコードの生成まで先に通し、dev で動くことを人が確かめて承認してから**、ほかの Unit に進む。

> 💡 教材ポイント: Construction のステージ（Functional Design、NFR Requirements、NFR Design、Infrastructure Design、Code Generation）は Unit ごとに行う。「ステージごとに進める」（stage-major）なら、1 つのステージを全 Unit で終えてから次のステージに進み、承認はステージごとに 1 回。ただし細い版の Unit は例外で、先に最後まで通す。

### レビュー（Architecture Reviewer Agent・adversarial）
1 回目の結果: **NOT-READY**（Major 3・Minor 2）。

| ID | 重大度 | 指摘 |
|---|---|---|
| R-01 | Major | 画面が Cognito を直接呼ぶ設計にしたため、約束（C1 の `/v1/session` の道と初回の手続きの印）とずれた。Cognito のリフレッシュトークンは「使うたびに 30 日延長」できない |
| R-02 | Major | 確実に届ける仕組みが報告の保存の知らせだけで、承認の知らせが失敗すると一覧が「確認中」のまま |

| R-04 | Minor | 送信の時間の合計の見積もりが甘く、関数の時間切れの設定がない |
| R-05 | Minor | 署名付きの PUT の URL では、アップロードの大きさを制限できない |

### 作り手の修正
- R-01: 約束どおり `/v1/session` の道を作り、Accounts の関数が Cognito を呼ぶ。Cognito の **refresh token rotation**（出し直しのたびに新しい 30 日のトークン）で「最後の利用から 30 日」を満たす
- R-02: 承認にも同じ仕組み（eventSent の印、3 回のやり直し、同じ依頼元の送り直しで再送）を入れた。操作の記録の知らせは失敗してもログだけ（受け入れたリスク）
- R-03: 送信のキーの状態の表（なし／作成中〈30 秒の期限〉／保存済み・知らせまだ／済み）を作り、保存と写真の結び付けを DynamoDB のトランザクションで同時に行う
- R-04: 時間の予算を計算し直し（最悪 約 5.8 秒）、API の関数の時間切れを 8 秒、知らせの受け手を 10 秒に
- R-05: 署名付きの **POST**（ポリシーで 15 MB の上限を S3 が強制）に変更

2 回目のレビューを実行。
2 回目の結果: **READY**。R-01〜R-05 はすべて解決。新しい指摘: Major 1（署名付きの POST に変えたが、約束の `POST /v1/photos` の応答に POST 用の項目がなく、写真の S3 の CORS も POST を許していない）、Minor 1（2 つのタブで同時に出し直すと、トークンの更新でログアウトされることがある）。

> ⚠️ ハマりどころ: adversarial のレビューは「Major が 2 件以下」なら READY になるため、直した結果として新しい Major が 1 件出ても READY で終わる。READY の記録のあとに成果物を書き換えると記録が無効になるので、残った指摘はステージの承認ゲート（全 Unit の完了後）で人が判断する。

### U3: 要件の「根拠」と設計の「実際の処理」がずれる

NFR 要件は「取り消しは条件にした書き換えだけだから、承認より速い（2 秒）」という理屈で目標を決めていたが、実際の設計は承認・却下と同じ「知らせの送信を待ってから応答する」という、要件の理屈が成り立たない処理経路になっていた。レビューは「p95 では収まる」という実測によらない取り繕いを見抜き、人に判断を求めた。人は「いま設計を直す」を選び、**取り消しだけ、知らせの送信を 1 回だけ試して待たずに応答する**という、要件の理屈（書き換えだけだから速い）と設計を一致させる変更を行った。この変更が「一覧の表示がまれに古いまま残りうる」という新しい小さなリスクを生んだため、受け入れたリスクとして明記し、ログの項目も足した。

> 💡 教材ポイント: **数値の帳尻合わせ（p95だから大丈夫、という言い訳）ではなく、要件の「なぜその数値か」という根拠と設計の実際の処理を一致させる**よう、人が判断して設計を直した。小さな設計変更が新しいリスクを生むこともあり、それを隠さず文書に書き残すことが大切。

### U4: 直した跡が別の文書に矛盾を残す

管理者アカウントの `loginId` の重なりを防ぐために、DynamoDB 側に専用の内部項目（`LoginIdLock`）を置く設計を一度書いたが、レビューで「新しい表は 2 つだけ、という他の文書の記述と矛盾する」「なぜ必要なのか根拠が書かれていない」と指摘され、**Cognito 側がすでにユーザー名の重複を保証する**ことに気づいて設計ごと撤回した。ところが、この撤回が機能設計（BR11.2）・データの形（entities.md）という**すでに確定した別の文書の字面**とは整合しないまま残り、開発者が古い文書を読んで要らない仕組みを作りかねない状態になった。確定済みの機能設計を書き換える代わりに、Code Generation が実際に参照する文書（performance-design.md）に、要件の文言と設計の実現方法の対応関係を明記する形で解消した。

> 💡 教材ポイント: **1 つの文書を直しても、関連する別の文書（とくにすでに確定したもの）に矛盾の跡が残ることがある。** 確定済みの文書を気軽に書き換えないという規律と、「次の工程（Code Generation）が実際に読む文書はどれか」を意識して直しを置く場所を選ぶことの両方が必要になる。

### ⚠️ ハマりどころ: 自動のトレーサビリティの取りこぼし

NFR Design の traceability.json をツール（`aidlc engine sensor-traceability --write-upstream`）で自動生成すると、observability-requirements.md 由来の要件 ID（`NFR10.2x`・`NFR11.1x`・`NFR14.x` など）が一貫して拾われない、というツール側の取りこぼしを U3・U4 で確認した。該当する要件 ID を手作業で確認し、traceability.json に追記して対応した。自動化されたチェックも完全ではないことを前提に、内容を目で確かめる手間を省かない。

これで NFR Design も全 Unit が READY になり、承認を得て Infrastructure Design に進む。

## 15. Infrastructure Design（全 Unit）の完了

NFR Design の決定を、U1 ですでに確定した AWS の構成（5 つの CDK スタック、`review`・`catalog`・`reporting`・`duplicate-detection`・`accounts`・`settings` の各 Lambda 関数）に具体的に落とし込む段階。U2〜U4 で、新しいスタックは一度も作らず、既存のスタックに表・関数・API の道を足すだけで済んだ。

| Unit | レビューの回数 | 最終 | 指摘の数 |
|---|---|---|---|
| U2 報告と重複 | 2 回 | READY | Critical 1・Major 1・Minor 1 → 全て解消 |
| U3 確認と一覧 | 2 回＋ステージゲートでの追加修正 | READY | Critical 1・Major 1・Minor 1 → 全て解消、新 Minor 1 → 解消 |
| U4 アカウントと管理 | 2 回＋ステージゲートでの追加修正 | READY | Major 2・Minor 3 → 全て解消 |

### 「設計書の前提」と「実際の構成」が食い違う、という繰り返しのバグ

このステージで一番多く見つかったのは、**NFR Design が前提にしていた関数の構成と、U1 で実際に確定していた構成が食い違っていた**ことによる指摘だった。U3 の nfr-design の質問（Q1）を書くときに「Review と ReportCatalog はすでに同じ関数にまとまっている」と誤って書いてしまい、この誤った前提が U3 の NFR Design 全体に広がり、U4 の NFR Design にもそのまま引き継がれていた。実際には U1 は `review`（承認、ReviewDecision の表だけ）と `catalog`（一覧、ReportListItem の表だけ）を最初から別々の関数にしていた。

このズレは、Infrastructure Design で IAM の権限を具体的に決める段階になって初めて「このままでは実行時に AccessDenied になる」という実害のある形で表面化し、レビューがそれを捕まえた。確定済みの NFR Design の文章を無理に書き換えるのではなく、Infrastructure Design 側で「U1 の実際の構成に沿って読み替える」という訂正を明記し、あとから NFR Design 側にも同じ訂正を反映した。

> 💡 教材ポイント: **質問を書く段階での小さな勘違い（「すでに1つの関数にまとまっている」という前提）が、何層にもわたる設計書に伝播し、インフラの段階で実行時エラーとして表面化する**。レビューの仕組みが、機能の層・性能の層・インフラの層それぞれで独立にこの食い違いを捕まえ、都度直すことで、コードを書く前に全て解消できた。

### 決定論的なチェックと、AI によるレビューの判断が食い違った例

U3 の `traceability.json` について、AI のレビュアーは「`NFR9.4` という ID は存在しないので消すべき」と判断したが、決定論的なチェック（traceability センサー）は逆に「`NFR9.4` が足りない」と指摘した。根本原因を調べると、`performance-design.md` の入力の引用部分に、U2 のパターンをそのままコピーした誤った範囲表記（「NFR7.5〜NFR9.4」。実際の最後の項目は NFR7.7）が残っていたことが分かった。`traceability.json` 側で帳尻を合わせるのではなく、引用の誤記そのものを直すことで、両方の指摘が解消した。

> 💡 教材ポイント: AI のレビュー（意味を読んで判断する）と、決定論的なセンサー（機械的に文字列を拾う）は、**同じ症状を逆の結論で指摘することがある**。どちらか一方を鵜呑みにせず、根本原因（引用のコピペミス）まで遡って確かめることで、本当に正しい直し方が見つかった。

U2〜U4 で、**Critical 2 件・Major 4 件・Minor 5 件**が Infrastructure Design 段階で見つかり、すべて直った。これで Infrastructure Design も全 Unit が READY になり、承認を得て Code Generation に進む。

## 16. Code Generation の立ち上がり（U2・U3）と、長時間セッションでの運用の教訓

Code Generation は、それまでの設計のステージと仕組みが大きく異なる。計画（どのファイルをどう変えるか、TDD の Red→Green→Refactor の順番）を人が承認したあと、Unit ごとに**独立した git の作業コピー（worktree）**を作り、それぞれ別のエージェントが並行してコードとテストを実際に書く（「swarm」という仕組み）。U2・U3 の計画承認後、この並行実装を開始した際に、設計のステージにはなかった種類のつまずきが重なったので、次回のために記録しておく。

### つまずき1: コードを書く前に、記録ファイルの未コミットでブロックされる

並行実装用の作業コピーを作る `swarm prepare` は、**プロジェクトの git の状態が完全にコミット済み（未追跡ファイルが一切ない）でないと実行を拒む**。これは、作業コピーが「コミットされた時点のスナップショット」から作られるため、未コミットの変更（たとえ無関係に見えるものでも）が作業コピーに反映されず、食い違いが起きることを防ぐための仕組みだと考えられる。

このプロジェクトでは、ここまでの NFR Design・Infrastructure Design・Code Generation の計画など、大量の記録ファイル（`aidlc/` 配下）が未コミットのまま溜まっており、これが直接の原因でブロックされた。team.md の通常のルール（作業ブランチ＋PR）に対し、「記録ファイルだけなので直接 main にコミットする」という判断を人が下し、コミットして解消した。加えて、Windows 側で誤って作られたとみられる空のテキストファイル（`新規 テキスト ドキュメント.txt`）も、未追跡ファイルとして同じブロックの原因になっていたため、削除して解消した。

> 💡 教材ポイント: **「コードは書いていないから git の状態は気にしなくていい」は AI-DLC の Code Generation には通用しない。** 設計のステージをいくつも進めたあとは、Code Generation に入る前に一度、記録ファイルをまとめてコミットしておくと、このブロックを避けられる。未追跡ファイルは、見覚えのないものでもまず中身と日時を確認し、誰が・いつ作ったものかを特定してから判断するとよい（このケースでは、セッション開始時点の git の状態を遡って確認し、AI が作ったものではないと特定できた）。

### つまずき2: 長時間の1セッションでのcontext管理

NFR Design・Infrastructure Design・Code Generation の計画作成までを、ずっと同じ1つの会話（セッション）で続けた結果、会話の履歴（メッセージ）がcontextの大半を占めるようになり、Claude Code自身が「contextが80%・89%に達した」という警告を出すに至った。

AI-DLCの仕組み自体（各ステージでAIレビュアーを呼び、指摘が出れば直してまた呼ぶ、という反復）は、1つの変更を確実にするために反復を多く行う設計であり、これが長時間セッションでのcontext消費を加速させる一因になっていると考えられる。一方で、**バックグラウンドで動く実装エージェント（Task経由で起動したサブエージェント）は、起動元の会話とは別の独立したcontextで動作する**ため、実装エージェント自体の処理速度は、起動元の会話のcontext使用量とは無関係である。

ただし、サブエージェントの結果（実装内容の確認、テストの確認、統合作業）を**起動元の会話で処理する**ことになるため、起動元のcontextが逼迫した状態のままその分析を行うと、見落としや精度低下のリスクが上がる。このプロジェクトでは、2つの実装エージェントを起動した直後にcontextが89%に達したため、**エージェントの完了を待つ間に、重要な内容をドキュメント（このファイル）に書き足してから `/compact`（会話の要約）を行う**、という対処をとった。`/compact`はセッション自体を終了させないため、バックグラウンドのエージェントからの完了通知を受け取る機能は保たれる（`/clear`や新しいセッションへの切り替えとは異なる点）。

> 💡 教材ポイント:
> - **設計フェーズ（NFR Design・Infrastructure Design など）が全Unit分終わった、Code Generationに入る直前**は、セッションを区切る・contextを整理する自然な境界になる。次回はこのタイミングで一度`/compact`するか、新しいセッションに引き継ぐことを検討するとよい。
> - **バックグラウンドの実装エージェントを起動したら、完了を待つ間に`/compact`しても作業は失われない**（起動元の会話が要約されるだけで、エージェント自体は別contextで動き続け、セッションも継続する）。「エージェントを待っている空き時間」は、contextを整理する良い機会になる。
> - この会話の生の記録（すべてのやり取りの詳細）は、`/compact`をしても、Claude Codeが保存しているセッションログ（JSONLファイル）としてディスク上には残り続ける。ただし、要約後の会話からはその詳細を参照できなくなるため、**教材として残したい重要な経緯は、要約の前にこうしたドキュメントへ明示的に書き出しておく**ことが大切（このセクション自体がその実例）。

### 実際に `/compact` を実行した記録

上記の教材ポイントを書き足した直後、実際にこのセッションで `/compact` を実行した。結果は次のとおりで、想定どおりだった。

- 会話の要約（コンパクト）は正常に完了し、セッション自体は終了しなかった。
- バックグラウンドで動いていた U2・U3 の実装エージェント（Task経由のサブエージェント）は `/compact` の前後を通じて動作を継続しており、完了通知を受け取る仕組みも維持された。
- AI-DLC 側の PreCompact フック（`aidlc engine hook validate-state`）が `/compact` のタイミングで自動的に実行され、正常終了した。要約によって状態ファイル（`aidlc-state.md` など）の整合性が壊れていないかを、コンパクトの直後に機械的に確かめる仕組みがあることが確認できた。

> 💡 教材ポイント: `/compact` は「会話を短くする」だけでなく、AI-DLC 側にも **コンパクトの前後でワークフローの状態が壊れていないかを確認するフック** が用意されている。長時間セッションの運用では、こうした仕組みがあることを前提に、`/compact` を「危険な操作」ではなく「安全に使える区切りの手段」として積極的に使ってよい。

## 17. U2・U3 の Code Generation 完了・マージと、AI-DLC2 の「学習の仕組み」

U2（report-duplicate）・U3（review-list）の実装がバックグラウンドの開発エージェントで完了し、`aidlc engine swarm check`で収束（converged）を確認した。しかし、そのままでは`aidlc engine swarm finalize`がmainへの統合を拒んだ。

### finalize は「テストが通った」だけでは収束と認めない

`finalize`を実行すると `"claimed converged but no terminal REVIEW_COMPLETED for stage \"code-generation\"... exists"` というエラーになった。swarmの仕組みでは、各Unitの実装を書くエージェント（developer）とは**別に、`aidlc-architecture-reviewer-agent`によるアーキテクチャレビューを明示的に実行し、READY判定を記録してからでないと、finalizeは「収束」と認めない**。これは`.claude/aidlc-common/protocols/stage-protocol-swarm.md`の「Autonomous reviewer boundary」節に定められた手順で、テストが通ることと、設計通りに作られているかをレビュアーが確認することは別の関門として扱われている。

`aidlc engine log review --project-dir <worktree>`でレビュー依頼を記録し、レビュアーをそのUnitのworktree（独立した作業コピー）に対して起動し、READY判定を得てから記録する、という手順を踏んで初めてfinalizeが通った。

> 💡 教材ポイント: swarm（並行実装）の「収束」は、**テストが通ること（check）と、設計レビューが通ること（finalize前提のreview）の2段構え**になっている。片方だけでは次に進めない。

### 並行して作られた2つのUnitのマージは、競合して当然

U2・U3は同じ`main`のコミットから分かれたworktreeで並行して作られたため、両方が触った共通ファイル（`backend/src/handlers/consumers.ts`・`contracts/openapi.yaml`・`frontend/requester/src/api.ts`・`frontend/requester/src/pages/DetailPage.tsx`・`frontend/ui-kit/src/components/ReportDetail.tsx`）で、`aidlc engine worktree merge`がgitの競合を検出した。中身を精査すると、ほとんどは「互いに無関係な追加同士」で、単純に両方を残せばよいものだった。ただし`ReportDetail.tsx`では、U3側の差分の中に、U3が実際には変更していない「U1からそのまま残っていた行」が紛れ込んでおり、見た目は競合マーカーの中にあっても実際にはU2側の内容（写真ギャラリー表示）をそのまま採用すべき箇所だった。3者（base・U2・U3）を見比べて初めて正しい解消方法が分かった。

マージ後に`npm run typecheck`・`npx vitest run`を実行すると、`stacks.u3.test.ts`の3件が失敗した。これはU3のインフラ構成試験が「U1だけを基準に、U3は関数も表も増やさない」という自己完結した前提で書かれており、同時に作られたU2が増やした分（関数4つ・表5つ）を数に入れていなかったため。件数をU1+U2+U3の合計に直して解消した。

> 💡 教材ポイント: 複数のUnitをswarmで**並行して**Code Generationすると、各Unitは互いの変更を知らないまま書かれる。マージ後は機械的な競合解消だけでなく、**全体を通したテストの再実行と、前提が古くなったアサーション（件数など）の手直し**が必要になる。

### 承認した計画に「重大なスコープの欠落」が埋もれていた

U2のレビューで、「ハンター側の報告ウィザード画面が8画面中3画面しか作られておらず、今の画面では完全な報告を送信できない（バックエンドの検証で拒まれる）」という指摘が出た。調べると、この制約は**実装前の承認済み計画書（code-generation-plan.md）にすでに明記**されていた。つまりレビューは正しく機能したが、**計画承認を求めた際に、この重大な制約を人に対して明示的に説明していなかった**のは、AIDLC2のorchestrator（この会話のAI）自身の落ち度だった。計画書に書いてあることと、人に承認を求める際の説明は別物であり、後者を省略してはいけない。

### AI-DLC2には「失敗を繰り返さない」ための正式な仕組みがある

ここまでの一連の経緯を踏まえ、人から「AI-DLC2には、開発の失敗を記録して繰り返さないようにする仕組みが実装されているのか」という質問があった。答えは**イエス**で、`docs/`配下のこの教材ドキュメント（人間が読むための記録）とは別に、AI-DLC2本体には`aidlc engine learnings surface`/`persist`という正式なコマンドがあり、ステージ完了時に「何を学んだか」を`org.md`/`team.md`/`project.md`の`## Corrections`セクションへ、日付と追跡用ID付きで恒久的に書き込める。**この記録は次回以降のすべてのセッション・すべてのステージが自動的に読み込むルールになる**点が、人間向けの教材ドキュメントとの決定的な違いである。

このセッションではこの仕組みを終盤まで使っていなかった（目の前のUnitを前に進めることを優先し、一歩引いて教訓を記録する判断を怠っていた）ため、ここまでの主な教訓5件を改めて`learnings surface`/`persist`で記録した:

1. 新しいUnitのNFR Designを書く前に、前のUnitの実際の`infrastructure-specification.md`でLambda構成を確認する（思い込みで「統合されている」と書かない）
2. Code GenerationのPlan Approvalでは、計画書に埋もれた重大なスコープ決定を、承認を求める説明の中で明示する
3. `cdk.out/`はビルド成果物であり、`.gitignore`にあるのにgit管理下に入っていた場合は`git rm --cached -r`で外す
4. 複数Unitをswarmで並行実装した場合、マージ後は全体テストを再実行し、他Unit分を数に入れていないアサーションを直す
5. per-unitレビュアーを起動する前に`<record>/.aidlc-engine/reviewer-dispatch.json`を書く（`stage-protocol-reviewer-unit.md`の必須手順。このセッションでは23回忘れており、`aidlc --doctor`の警告で発覚した）

> 💡 教材ポイント: 「便利な機能があるのに使っていなかった」のは設定の問題ではなく、**エージェント（AI）自身がステージ完了のたびに一歩引いて「これは恒久的なルールにすべきか」と考える習慣を持てていなかった**ことが原因だった。`aidlc --doctor`は、こうした手順の踏み忘れ（レビュアー起動前の記録ファイルなど）を事後的に検出してくれるため、長時間セッションの区切りごとに実行する価値がある。
